# Extraction is a proposal, not a fact

The worker used to write whatever the model returned straight onto the document and move it to `ready`. A guess and a fact ended up in the same columns, indistinguishable afterwards, and nobody was ever asked. That is fine while the model is right and silently corrupting when it is not: an invented sender is stored with the same authority as one a person typed, and the only signal that anything happened is that a search stops finding a document somebody knows they filed.

So an extracted value is now a **proposal** with a confidence, stored in `document_extractions` next to the document rather than on it. Only what clears `auto_accept_confidence` is written to the document; anything between that and `review_confidence` is offered to a person; anything below is recorded but not shown, because a guess weak enough to be worthless would still anchor whoever reads it. The lifecycle already had a `review` state from the canonical ingestion work with nothing that could reach it — this is what lights it up.

**The thresholds live in the database, not in code.** Two processes have to agree on them: the Python worker that produces extractions and the TypeScript backend that serves the inbox. A constant in either one is a constant the other can contradict, and "configurable" would mean a deployment. `review_settings` is a single row, `review_decision_for()` is the single comparison, and `record_extraction()` is the only way in — so moving a threshold moves every producer at once, and an administrator moves it from the UI.

**Confidence is checked against the document, not taken on trust.** A model's self-reported certainty is an opinion about its own opinion. For fields whose value must literally stand in the document — sender, recipient, both dates, the amount — the worker looks for the value in the OCR text and multiplies an ungrounded claim down to a fraction of what was claimed. An invented sender therefore lands in the inbox no matter how sure the model said it was. The regex fallback that runs when no provider answers carries its own deliberately modest scores: a matched keyword is real evidence and worth proposing, but it is never worth writing to the archive unreviewed, so an offline provider fills the inbox instead of the document.

**Duplicates are two different questions.** The same bytes arriving twice is a certainty, and the hash proves it at ingest — where the second original is not written at all, because ingestion hardlinks into the copies it already verified. The same content arriving as a different file is a judgement, so it is only ever a candidate. Nothing in this feature merges, replaces, or deletes a document: confirming a candidate links the pair, separating one records that they are different, and both documents are still there afterwards either way. The pair, in either direction, is the identity — so an answered question, especially "these are not the same", is never asked again.

Similarity is a plain Jaccard overlap of the OCR token sets over a bounded candidate list rather than an index. A household archive is thousands of documents, not millions, and an exact score anyone can recompute by hand beats an approximate one nobody can argue with. It runs from a scheduler on the backend rather than inside the worker: the comparison needs the stored text of every other document, and putting it on the worker's processing path would make a slow neighbour scan look like a slow OCR run.

**Detection never crosses a space boundary.** "You already have this file" is information about the contents of a space. Telling an administrator that about a private space would walk straight around the rule that made private spaces private — upload a copy of what you suspect is in there, and the system confirms it for you. Duplicates are found within a document's own space, and the common area is a space like any other for this purpose. The inbox itself is a document list and answers to the same rule: a question about a document you may not read is not in your inbox, and a duplicate counterpart you may not read is reported as existing but never named, the same trade the audit log already makes.

A document in `review` stays visible, searchable and readable. The lifecycle wording — "a human decision is required before normal use" — is about the *metadata*, not about the file: hiding a document somebody just filed, because a model was unsure whether the sender was a GmbH or an AG, would look exactly like losing it, and with no LLM configured at all it would hide nearly everything. What `review` withholds is the uncertain value, which was never written; what it adds is a visible question. Only `archived` and `trashed` remove a document from normal use, and that has not changed.

**The queue is a table.** `review_items` holds the open questions, `document_extractions` holds what was proposed and what was actually applied, and `documents.similarity_scanned_at` marks what has been compared. Nothing about pending work lives in a process, so a worker restart, a provider outage, or a backend deploy changes nothing about what is still owed — the worker simply runs the same statements again, and both `apply_document_extractions()` and `settle_document_review()` are idempotent, so re-running them neither double-applies a value nor stacks a second copy of the same question.

One consequence is accepted rather than worked around: a reviewer's correction is stored as an extraction at full confidence with `provider = 'human'`, and a later re-extraction of the same document supersedes it. That is deliberate. A retry is somebody explicitly asking for the document to be read again, usually because the text was wrong; silently keeping a correction made against text that no longer exists would be the more surprising answer.
