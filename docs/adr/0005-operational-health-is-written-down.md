# Operational health is written down, and an alert is a local record first

DocVault already knew whether each of its dependencies was working — it simply never wrote that knowledge anywhere an operator could see it. `/api/health` said the process was up, which is the one failure mode a running process cannot have. The interesting states are the ones where the process is fine and something behind it is not: the worker stopped consuming, the replica volume filled, the last verified restore is three weeks old, the mailbox poll has been failing since Tuesday.

**Health is stored, not computed per request.** `ops_component_health` holds the latest probe result for each of the eight dependencies. That is what makes "last success" answerable *while the component is down*: a live probe of a dead Redis can report the failure and nothing else, and "when did this last work" is exactly what an operator needs to know first. Each row carries the measured metrics, the current failure, and a short German **recovery action** — a dashboard that says `worker: failed` and stops there has told the reader nothing they can act on.

**Deduplication is a database guarantee, not an application convention.** A partial unique index gives one open incident per `(component, kind)`, so the alerting path is an upsert: a problem that is already known bumps `occurrences` and `last_seen_at` and sends nothing. Without that constraint, "don't send the same alert twice" is a rule every future code path has to remember, and a monitoring system that mails every five minutes gets filtered into a folder nobody reads — which is worse than no alerting, because it looks like alerting. Recovery is the same shape in reverse: closing an incident sends exactly one notice, guarded by `recovery_notified_at`.

**An alert is a local record first and an email second.** The incident row is written before any delivery attempt, and each attempt appends its own row with `delivered`, `failed`, or `skipped` plus a reason. So a household running with no mail server at all — the default, since `SMTP_HOST` is empty — loses nothing: the incident is in the dashboard, marked as undelivered. This is the difference between a monitoring system that fails safe and one whose failure mode is silence.

**Operational data is counts, ages and bytes.** No table here holds a document id, title, filename, sender or space name, and neither do the alert bodies. An admin operations dashboard is exactly the kind of surface that becomes a side channel around tag ACLs and the private-space rule: "3 Dokumente in Verarbeitung seit 40 Minuten" is what an operator needs, and naming them would hand an administrator content they are otherwise not allowed to read. Tests assert the absence, rather than trusting the current queries to stay that way.

Two limitations are accepted rather than papered over. **Worker liveness is inferred** from the transitions the worker writes, because the worker has no heartbeat: an idle worker and a dead one are indistinguishable until work arrives, so the probe only fires when documents are actually waiting. A heartbeat belongs to the worker's own change, not to the dashboard that would consume it. And **a failed delivery is not retried**, because retrying is what the dedupe rule exists to prevent; a mail outage during the first observation of a problem means the incident lives in the dashboard until it recurs.
