# Trash is a lifecycle state, purge is a separate authorized action

Deleting a document moves it to the `trashed` lifecycle state and touches no bytes. The state machine records `pre_trash_status`, so a restore returns the document to exactly the state it held before, and materializes `purge_after` (90 days) at trash time so the recovery deadline stays stable even if the policy changes. Restoring is still allowed after the window elapses, because the content demonstrably still exists and refusing it would destroy value that no purge decision has approved.

Purge is the only operation that destroys content. It runs solely on trashed documents, requires the admin role plus a typed confirmation of the exact document id, and refuses under any of five guards: legal hold, retention lock, active share links (overridable only by revoking them as part of the purge), stored versions (destroyed and counted with the document), and backup policy — no successful backup on record means an override has to be acknowledged explicitly, because destroying the last two copies while backups are broken removes the only path back from a mistaken purge. The purge audit event is written before the row disappears and repeats document id, title, hash, file paths and the covering backup id, since `audit_logs.document_id` is nulled by the foreign key.

Nothing purges on a schedule. Day 91 makes a document *eligible*; an admin still has to run the purge. That keeps "deleted documents remain recoverable for 90 days" a floor rather than an expiry, and keeps every destructive act attributable to a person.
